# Traccar Client SDK → CourierTax feasibility audit

**Recommendation: CONDITIONAL GO for a small, measured proof of concept; not approval to ship background tracking.**

Audit performed **3 November 2026**. The supplied brief is dated 27 October 2026. Source inspected: `Susurik/traccar-client-sdk`, local branch `work`, commit `0e0db40ea6d58df47523af00c72716dae8c91213`. This report documents an audit only. No CourierTax implementation, application-source changes, dependency upgrades, commits, pull requests, device installs, or store submissions were made.

## 1. Executive summary

The selected repository is the **correct SDK**, and both native location implementations are real. The iOS implementation is substantially more than a stub: it uses Core Location, motion detection, region monitoring, and background-task scheduling. Android uses Google Fused Location or Android LocationManager, a service/notification, and optional motion, geofence, heartbeat, and wake-lock components. **VERIFIED BY CODE.**

However, this is primarily an **on-device tracker that uploads to a server**, not a ready-made offline mileage ledger. Its SQLite positions table is a retry queue: successful uploads delete points. React Native exposes control commands and diagnostic logs, but no raw-position subscription, route-history query, shift model, manual business-break API, or mileage total. **VERIFIED BY CODE.**

For CourierTax, the decisive answers are:

| Requirement | Finding | Evidence level |
|---|---|---|
| Real native iOS and Android tracking code | Yes, on both platforms. | VERIFIED BY CODE |
| Two-hour background tracking while locked, using courier/navigation apps and receiving calls | Plausible architecture, but **not demonstrated** on either physical platform in this audit. | INFERRED / UNKNOWN |
| Survive temporary internet loss without deleting already committed queued points | Buffered path persists accepted fixes before upload and waits/retries. Acquisition, disk-full, crash, and locked-device durability still need device tests. | VERIFIED BY CODE; actual device behavior UNKNOWN |
| Fully local GPS routes and mileage, with no Traccar server | **YES WITH CHANGES.** No server is inherently needed by the native GPS APIs, but the current SDK needs a supported local-recording/storage interface and an upload-disabled mode. | VERIFIED BY CODE for current gaps; proposed design INFERRED |
| Commercial React Native/Expo app | Legally and technically plausible with obligations, native integration work, and physical validation. Expo Go cannot host this custom native module. | CODE / DOCUMENTED ONLY / INFERRED |
| Drop-in iOS React Native installation | A material CocoaPods packaging gap was found; no signed iOS host build was executed to confirm its exact failure mode. | VERIFIED BY CODE/package inspection; build consequence INFERRED |
| Production reliability | **UNPROVEN.** Relevant upstream bug reports remain open, including an iOS stationary-resume failure mechanism still visible in this revision. | External reports + CODE; no reproduced device failure here |

**Practical recommendation:** build a fresh CourierTax React Native/Expo application, keeping the GPS engine behind a small interface. First compare a serverless Expo Location/TaskManager baseline with a bounded Traccar-engine prototype. A commercially supported background-location module is another candidate if its licence cost is acceptable. Do not fork the full Traccar app or Comma simply because they contain existing screens. Do not start tax, subscription, or bookkeeping implementation until the GPS experiment meets the acceptance criteria below.

## 4. How tracking and persistence actually work

### 4.1 Shared pipeline and server dependency

**VERIFIED BY CODE.** The basic path is native location callback → in-memory flow → shared filter/battery processing → SQLite queue when `buffer=true` → HTTP upload → delete queued row after a successful HTTP status. The engine's uploader is unconditionally bound to `HttpUploader`; there is no local-only configuration option. [CoreModule.kt:8–28](https://github.com/Susurik/traccar-client-sdk/blob/0e0db40ea6d58df47523af00c72716dae8c91213/core/src/commonMain/kotlin/org/traccar/client/CoreModule.kt#L8-L28) [TrackerEngine.kt:72–108](https://github.com/Susurik/traccar-client-sdk/blob/0e0db40ea6d58df47523af00c72716dae8c91213/core/src/commonMain/kotlin/org/traccar/client/TrackerEngine.kt#L72-L108) [DatabaseQueue.kt:16–56](https://github.com/Susurik/traccar-client-sdk/blob/0e0db40ea6d58df47523af00c72716dae8c91213/core/src/commonMain/kotlin/org/traccar/client/DatabaseQueue.kt#L16-L56)

`Config` requires `serverUrl` and `deviceId`, but `Tracker.start()` only enables persisted state; it does not require a successful server handshake. Therefore **a working server is not required to begin acquiring/queuing locations**. That is different from a supported, complete serverless mode. A blank or deliberately unreachable URL merely causes failed upload attempts and a growing queue; it is not a sound CourierTax design. `buffer=false` attempts direct upload and discards failures, so it is not an offline-first switch. [Config.kt:6–15](https://github.com/Susurik/traccar-client-sdk/blob/0e0db40ea6d58df47523af00c72716dae8c91213/core/src/commonMain/kotlin/org/traccar/client/Config.kt#L6-L15) [Tracker.kt:24–27](https://github.com/Susurik/traccar-client-sdk/blob/0e0db40ea6d58df47523af00c72716dae8c91213/core/src/commonMain/kotlin/org/traccar/client/Tracker.kt#L24-L27) [TrackerEngine.kt:79–108](https://github.com/Susurik/traccar-client-sdk/blob/0e0db40ea6d58df47523af00c72716dae8c91213/core/src/commonMain/kotlin/org/traccar/client/TrackerEngine.kt#L79-L108)

**VERIFIED BY CODE.** Buffered failures back off from 5 seconds to a maximum of 5 minutes; an offline network monitor makes the uploader wait for connectivity. Every HTTP 2xx response is considered success. The queue is FIFO and deletes the oldest row on success. [TrackerEngine.kt:28–29](https://github.com/Susurik/traccar-client-sdk/blob/0e0db40ea6d58df47523af00c72716dae8c91213/core/src/commonMain/kotlin/org/traccar/client/TrackerEngine.kt#L28-L29) [TrackerEngine.kt:89–108](https://github.com/Susurik/traccar-client-sdk/blob/0e0db40ea6d58df47523af00c72716dae8c91213/core/src/commonMain/kotlin/org/traccar/client/TrackerEngine.kt#L89-L108) [HttpUploader.kt:16–39](https://github.com/Susurik/traccar-client-sdk/blob/0e0db40ea6d58df47523af00c72716dae8c91213/core/src/commonMain/kotlin/org/traccar/client/HttpUploader.kt#L16-L39) [Position.sq:18–26](https://github.com/Susurik/traccar-client-sdk/blob/0e0db40ea6d58df47523af00c72716dae8c91213/core/src/commonMain/sqldelight/org/traccar/client/db/Position.sq#L18-L26)

**INFERRED risks:** an indefinitely failing head item can block later uploads; a lost success response can cause duplicate server submissions; there is no end-to-end idempotency identifier/acknowledged route protocol. Network “online” does not prove the server is reachable. Retries stop when the OS suspends/kills the app; this is not an independent background daemon.

### 4.3 Filtering and business-distance accuracy

**VERIFIED BY CODE.** The shared filter accepts a first fix, the first fix after a native stationary-state change, or a positive time **or** distance **or** bearing-change threshold. Its Haversine function only compares two positions for filtering; it does **not** sum travelled distance. There is no specific rejection for poor/negative accuracy, implausible speed, large jumps, stale/duplicate timestamps, tunnelling, or map matching. [LocationFilter.kt:20–76](https://github.com/Susurik/traccar-client-sdk/blob/0e0db40ea6d58df47523af00c72716dae8c91213/core/src/commonMain/kotlin/org/traccar/client/LocationFilter.kt#L20-L76)

Defaults are medium accuracy, 75 m distance, 300 s interval, angle disabled, automatic stop detection enabled, 60 s stop timeout, 100 m stationary radius, heartbeat disabled. Provider-effective settings prefer the distance trigger over interval, and HIGHEST removes native distance/interval constraints. The shared filter still uses the original config. Setting all three shared thresholds to zero does **not** mean “save everything”: after the first point, ordinary fixes have no acceptance trigger. [Config.kt:24–47](https://github.com/Susurik/traccar-client-sdk/blob/0e0db40ea6d58df47523af00c72716dae8c91213/core/src/commonMain/kotlin/org/traccar/client/Config.kt#L24-L47) [LocationFilter.kt:16–48](https://github.com/Susurik/traccar-client-sdk/blob/0e0db40ea6d58df47523af00c72716dae8c91213/core/src/commonMain/kotlin/org/traccar/client/LocationFilter.kt#L16-L48)

**INFERRED:** those defaults suit periodic position reporting more than dense courier routes. Sparse points cut corners; GPS drift and jumps add false distance; no GPS means the route through a tunnel is unknown. Automatically stationary is not the same as a work break. Preserve quality flags and interruption gaps rather than silently joining far-apart points or reporting estimated tunnel distance as measured GPS distance. Battery and distance tradeoffs must be measured for walking, cycling, scooters, and cars; no consumption/error figures were measured here.

### 4.4 Start, pause, stop, recovery, and off-shift safety

**VERIFIED BY CODE.** `start()` sets `enabled=true`; `stop()` sets `enabled=false, paused=false`. Automatic stationary signals toggle `paused` while enabled. The public API does not expose a manual shift/break state machine. `isTracking()` reports a persisted logical flag, not confirmation of live GPS or correct permission. [Tracker.kt:22–32](https://github.com/Susurik/traccar-client-sdk/blob/0e0db40ea6d58df47523af00c72716dae8c91213/core/src/commonMain/kotlin/org/traccar/client/Tracker.kt#L22-L32) [TrackerEngine.kt:49–61](https://github.com/Susurik/traccar-client-sdk/blob/0e0db40ea6d58df47523af00c72716dae8c91213/core/src/commonMain/kotlin/org/traccar/client/TrackerEngine.kt#L49-L61) [Component.kt:23–29](https://github.com/Susurik/traccar-client-sdk/blob/0e0db40ea6d58df47523af00c72716dae8c91213/core/src/commonMain/kotlin/org/traccar/client/Component.kt#L23-L29) [index.tsx:110–147](https://github.com/Susurik/traccar-client-sdk/blob/0e0db40ea6d58df47523af00c72716dae8c91213/react-native/src/index.tsx#L110-L147)

Stop also preserves the filter's last accepted location. A new shift's first fix can therefore be compared with the previous shift and filtered rather than accepted immediately; reset or reconcile that history at the shift boundary. **VERIFIED BY CODE / INFERRED consequence:** [LocationFilter.kt:16–44](https://github.com/Susurik/traccar-client-sdk/blob/0e0db40ea6d58df47523af00c72716dae8c91213/core/src/commonMain/kotlin/org/traccar/client/LocationFilter.kt#L16-L44) [Tracker.kt:29–32](https://github.com/Susurik/traccar-client-sdk/blob/0e0db40ea6d58df47523af00c72716dae8c91213/core/src/commonMain/kotlin/org/traccar/client/Tracker.kt#L29-L32).

CourierTax must own explicit shift and segment records. A user pause must remain paused until the user resumes; it must not automatically resume because the device moves. Stop/start can be used as recorder controls in a prototype, but require a separate manual-break ledger and a tested restart boundary. Do not count a queue-waiting/upload period as working time.

Two easily missed exceptions matter:

1. `requestPosition()` works independently of start/stop and directly fetches/uploads a fix. It is not buffered and returns upload success, not a raw GPS point. ## 7. Offline-first verdict and precise changes needed

### Verdict: YES WITH CHANGES; unmodified supported local-only usage is not established

The operating systems can provide location without a Traccar server. This SDK already contains reusable acquisition and SQLite machinery. However, CourierTax cannot safely treat the upload queue or diagnostic text as a route database. An unreachable URL, no-op uploader, or logs-parsing workaround does not meet the requirement.

| Proposed change, not implemented | Why it is needed | Approximate scope |
|---|---|---|
| Add an explicit `LOCAL_ONLY` recorder mode; do not construct/run the HTTP synchronization path in that mode. Make endpoint/device config optional or separate for upload use. | Prevent unwanted network calls, fake endpoints, retry storms, and deletion-as-ack semantics. Changing only the JS wrapper cannot change the native engine's binding. | MEDIUM, native shared-core API change |
| Add a durable route journal with shift ID, segment ID, stable point ID, timestamps, quality data and monotonic session bookkeeping. Keep upload status separate from route retention. | History must survive successful uploads, app relaunch and no network; business distance must not connect separate shifts or breaks. | MEDIUM–HIGH |
| Commit points natively before notifying JS; expose paginated history/cursor reads, recorder-health/error/status events, export and deletion. Events supplement durable queries. | JS can suspend/crash; event-only listeners lose data. RN needs access without probing a private DB or parsing logs. | MEDIUM–HIGH |
| Make shift start/pause/resume/stop durable, serialized and distinct from automatic stationary power management. Gate all one-shot APIs. | Explicit user intent, no off-shift tracking, no movement-triggered resumption of a manual break. | MEDIUM–HIGH |
| Implement/test mileage and work-time calculation with accuracy/outlier/age rules, segment boundaries and recorded uncertainty. | Haversine between arbitrary retained points is not a complete business-distance algorithm. | MEDIUM–HIGH |
| Repair/verify RN iOS packaging, native early lifecycle registration and chosen Android permission/FGS behavior. | The app must actually build and remain in the permitted tracking state. | MEDIUM–HIGH; device-dependent unknowns |

These are targeted changes compared with building two acquisition stacks from scratch, but **more than a cosmetic wrapper**. `CoreModule` hard-wires its private composition; although `Uploader` and `PositionQueue` are interfaces, the public `sharedTracker(config)` API does not provide dependency injection for a consumer-supplied local store. ### 8.3 Store review risks

Commercial store distribution is **feasible in principle**, not pre-approved by Apache licensing or successful compilation. A courier explicitly starting a mileage shift has a plausible user-visible background-location purpose, but reviewers assess the shipped behavior and declarations.

For Apple, use accurate location/motion purpose strings, appropriate background modes, explicit user-started tracking, truthful privacy labels and a working off switch. If data is transmitted, disclose the actual purposes and recipients. ## 11. Physical-device acceptance plan — proposed, not executed

### 11.1 Test setup and measurement rules

Use an actual signed consumer app, not only the native sample or simulator. Test at least a Pixel/stock Android device and an OEM device with aggressive battery policy, across relevant Android permission/service generations (including Android 12, 13, 14+ and the chosen current target devices); include at least two physical iPhone/iOS generations supported by the chosen app minimum and current release. Exact hardware/OS selection depends on real courier usage. Include Google and platform-location provider paths if both will be supported.

Define the stop/pause boundary as an acknowledged durable user-intent transition. Handle in-flight fixes with their original acquisition time; shutdown must not silently extend the active segment or resurrect a stopped shift.

Before each run record app/engine SHA and package provenance, phone/OS, permissions including precise/Always/background/motion/notification, battery/power policy, location config, network state, and start battery/temperature. Record local point IDs/timestamps, durable commit counts, state/permission changes, process launches, errors, and segment boundaries. Use redacted diagnostics. Compare device and app clocks and ensure results belong to that run.

**Proposed initial gates, not measured performance promises:** for an accuracy-focused POC with a deliberately chosen dense sampling policy, require no unexplained moving-GPS gaps over 30 seconds when outdoor signal is available; investigate urban route-distance error above 5% and open-road error above 3% against an independent reference. Predefine a stationary-drift allowance and a battery budget after a paired baseline pilot. These values are experiment starting points, not SDK guarantees or tax certification. Document GPS outages as gaps rather than fabricating observations.

4. **Run one physical Android and iPhone reference route immediately.** Two hours locked/app-switching, a call, an offline interval, manual break, stop, export; compare committed points, known-route distance and battery. Start with automatic stationary optimization disabled to isolate acquisition, then repeat with it enabled to expose departure/relaunch issues. Do not use a demo server with real location data.
5. **Reproduce the three reported failure classes and permission-denial paths.** Prioritize iOS stale-region restart and RN launch hooks, Android foreground startup/stop race, notification-denial fallback, and stationary liveness. An update to 1.1.4 is not a substitute for those tests.
6. **Choose the engine based on results and ownership cost.** Proceed to CourierTax only if both physical platforms meet the ordinary-background/offline/manual-intent gates and interruptions are honestly represented. Expand device coverage, secure storage and release-policy checks before production.

**Stop/go gate:** if neither candidate can meet the normal locked-screen/background recording contract without unexplained losses, or the required native maintenance is unaffordable, do not proceed with the full product on that engine. A permitted OS force-quit interruption is handled as a disclosed limitation, not covered up as continuous tracking.

- Direct GitHub API and several Apple/Android/Expo public documentation endpoints returned proxy 403. GitHub web issue/release data and official documentation source files supplied the evidence described; this was not treated as proof that all issues/policies were reviewed.
- Upstream state after the checked 1.1.3 revision was observed separately; neither the checkout nor its dependency/lockfile pins were updated.
- Comma's exact repository/revision was unavailable. Its prior stub/licence findings remain supplied context, not independently reproduced findings.
- This is a report-only change in the SDK checkout. Scratch evidence/logs and downloaded public metadata/source archives live outside it under `/workspace/.audit-evidence`; generated existing ignored build outputs were refreshed. No real tracking was started and no third parties were messaged.

## Five plain answers

**1. Is Traccar's iOS background GPS code actually implemented?** Yes. Core Location background updates, significant-change monitoring, motion/regions and heartbeat code exist. Their reliability in a CourierTax consumer is unproven; RN integration and stationary/lifecycle gaps need work.

**2. Is Traccar's Android background GPS code actually implemented?** Yes. Native provider, service/notification, permissions, buffering and power-management code exist, and the Android sample build passes. That is not a physical background-tracking test.

**3. Can CourierTax be fully offline for GPS tracking and distance calculation without any Traccar server?** **YES WITH CHANGES.** The phone can record locally without a server, but the current SDK's upload queue/RN API do not provide the required permanent local route ledger. Add a supported local-only native store/API and shift/distance logic, or use another local-first engine. Do not use a fake URL or logs as the solution.

**4. Can the SDK be incorporated into a commercial React Native/Expo app for Latvia?** Yes in principle under Apache-2.0 and dependency obligations, using a native development/release build. Resolve iOS packaging/lifecycle and version alignment, pass both-device tests, and satisfy store/privacy requirements. Expo Go and compilation alone are insufficient; Latvian tax compliance is a separate task.

**5. Is Traccar SDK a better starting point than Comma for these requirements?** For the GPS engine, yes relative to the supplied finding that Comma's iOS implementation is a stub: Traccar has real code for both platforms. For the whole product, no blanket conclusion is justified. A fresh CourierTax app with a tested, replaceable GPS engine is the stronger starting architecture; selected Comma bookkeeping reuse needs its own source/licence review.
